2. Chọn 3 dự án: phủ đủ ba mảng kỹ năng

Ba dự án chất lượng, đầy đủ, có số liệu thuyết phục hơn mười notebook dang dở. Ba capstone của lộ trình phủ ba mảng mà một trạm vision thật cần:

Dự ánChứng minh kỹ năngCon số "đinh" trong README
Capstone 1: trạm đo kích thước hoàn chỉnhHiệu chuẩn, đo subpixel, phân tích hệ thống đo (MSA), Modbus TCP, biên bản nghiệm thu tự sinh%GRR, bias so với CMM, escape/overkill trên mẫu vàng, p99
Capstone 2: trạm đọc DataMatrix và số seriĐọc mã 2D, OCR/OCV, đối chiếu lệnh sản xuất, chống trùng bằng CSDL, đạt tốc độ dây chuyềnTỉ lệ đọc đúng, escape trên các loại nhãn lỗi, p99 so với nhịp 150 hộp/phút
Capstone 3: kiểm tra lỗi bề mặt bằng AI, trả kết quả PLCDữ liệu chia theo lô, huấn luyện, chọn ngưỡng theo escape, ONNX, giám sát driftEscape trên lô chưa thấy, overkill, sai lệch ONNX/PyTorch, thời điểm phát hiện mất nét

Nếu ứng tuyển vị trí thiên về AI, đặt Capstone 3 lên đầu; vị trí đo lường, kiểm tra chất lượng thì Capstone 1. Có thể thêm một dự án thứ tư thể hiện điều riêng của bạn (ví dụ dự án dùng camera và đèn thật, dù đơn giản: ảnh thật luôn gây ấn tượng hơn ảnh tổng hợp).

Dự án ở công ty: không đưa lên mạngMã nguồn, ảnh sản phẩm, dữ liệu khách hàng của dự án làm cho công ty thuộc về công ty và thường có cam kết bảo mật. Không đưa lên GitHub, kể cả "chỉ vài ảnh". Trong CV và phỏng vấn, mô tả ở mức tổng quát (loại sản phẩm, loại lỗi, kết quả, vai trò của bạn) và tái hiện kỹ thuật bằng dữ liệu tự tạo, như cách các capstone dùng ảnh tổng hợp.

3. README thuyết phục: bài toán, con số, quyết định, giới hạn

README của portfolio khác README bàn giao ở bài trước: người đọc là nhà tuyển dụng, nên kết quả và cách bạn suy nghĩ lên đầu, hướng dẫn cài đặt xuống dưới. Cấu trúc gợi ý:

  1. Một câu bài toán có số: sản phẩm, loại lỗi, tốc độ, tiêu chí.
  2. GIF demo 10–15 giây ngay dưới tiêu đề.
  3. Bảng kết quả: yêu cầu và giá trị đạt, cỡ mẫu, điều kiện thử.
  4. Kiến trúc: sơ đồ camera → xử lý → PLC/CSDL.
  5. Quyết định kỹ thuật và lý do: vì sao đèn này, thuật toán này, ngưỡng này; điều đã thử mà không hiệu quả.
  6. Giới hạn và bước tiếp theo: trung thực về dữ liệu tổng hợp, phần chưa thử.
  7. Cách chạy: một lệnh tái tạo toàn bộ kết quả.

Hiểu đúng các con số trước khi đưa vào README (người phỏng vấn sẽ hỏi):

Chỉ sốĐịnh nghĩaCách trình bày đúng
Escape (lọt lỗi)Số/tỉ lệ sản phẩm NG bị trạm cho là OK"0 / 412 ô NG trên 2 lô chưa dùng khi huấn luyện" (luôn kèm cỡ mẫu)
Overkill (loại nhầm)Tỉ lệ sản phẩm OK bị trạm loại"1,9% trên 1000 nắp OK"; nói rõ đánh đổi với escape khi chọn ngưỡng
Cycle time / p99Thời gian xử lý; p99 là mức mà 99% chu kỳ nhanh hơn"p99 31 ms trên PC 8 lõi, ngân sách 50 ms" (kèm phần cứng)
%GRRBiến thiên của hệ thống đo (lặp lại và tái lập) so với dung sai"%GRR 4,2% (≤ 10%: chấp nhận được), 3 chi tiết × 30 lần"

Ví dụ phần đầu README cho Capstone 3 (số liệu minh họa: dùng số trong biên bản của bạn):

# Kiểm tra lỗi bề mặt nắp nhôm bằng AI, trả kết quả cho PLC

Phát hiện xước/đốm trên nắp nhôm xước sợi ở 30 nắp/phút; trả OK/NG qua Modbus TCP;
mục tiêu escape = 0 trên lô vật liệu chưa từng thấy.

![Demo](docs/demo.gif)

## Kết quả (tập test: 2 lô chưa dùng khi huấn luyện)
| Chỉ số | Yêu cầu | Đạt |
|---|---|---|
| Escape | 0 | 0 / 412 ô NG |
| Overkill | ≤ 2 % | 1,9 % (1000 nắp OK) |
| Sai lệch ONNX so với PyTorch | ≤ 1e-4 | 4e-7, không quyết định nào bị lật |
| Suy luận 1 nắp (64 ô), p99 | ≤ 50 ms | 31 ms (CPU 8 lõi) |
| Cảnh báo mất nét | trước escape đầu tiên | sớm hơn 140 sản phẩm |

## Quyết định kỹ thuật
- Chia dữ liệu theo lô vật liệu, không chia ngẫu nhiên: chia ngẫu nhiên cho escape 0 "ảo",
  chia theo lô lộ ra 2,2 % escape với ngưỡng mặc định 0,5.
- Chọn ngưỡng theo escape trên tập val (0,31), chấp nhận overkill 1,9 %.
- Giám sát độ nét bằng EWMA: phát hiện camera mất nét trước khi tỉ lệ NG thay đổi.

## Giới hạn
Dữ liệu tổng hợp; chưa thử nắp màu đen; vết xước song song vân dưới 0,5 mm khó thấy.

## Chạy lại toàn bộ
`python run_all.py` – tạo dữ liệu, huấn luyện, xuất ONNX, chạy trạm với PLC giả, sinh biên bản.

  • Video 2–3 phút (YouTube không công khai, hoặc file trong mục Releases): 15 giây bối cảnh, chạy demo thật, chỉ vào con số nghiệm thu, một sự cố được xử lý (camera mất kết nối, PLC timeout). Quay màn hình độ phân giải đủ lớn, giọng nói rõ, không nhạc nền ồn.
  • Ảnh thật (dù chụp bằng webcam với đèn bàn) tạo khác biệt lớn. Ghi chú rõ ảnh nào là tổng hợp.

Hoặc tạo GIF trực tiếp từ các ảnh kết quả mà chương trình của bạn đã vẽ, bằng Pillow. Ví dụ dưới đây tự tạo 8 khung hình băng tải có khung OK/NG và thanh trạng thái:

from pathlib import Path

import cv2
import numpy as np
from PIL import Image

rng = np.random.default_rng(0)
khung_hinh = []
for i in range(8):
    anh = np.full((240, 400, 3), 60, np.uint8)
    cv2.rectangle(anh, (0, 90), (400, 190), (90, 90, 90), -1)                 # băng tải
    x = 40 + i * 40
    cv2.circle(anh, (x + 30, 140), 32, (190, 190, 190), -1)                   # nắp
    ng = i in (3, 6)
    if ng:
        cv2.line(anh, (x + 18, 128), (x + 40, 150), (40, 40, 40), 2)          # vết xước
    mau = (0, 0, 255) if ng else (0, 200, 0)
    cv2.rectangle(anh, (x - 6, 104), (x + 66, 176), mau, 2)
    cv2.rectangle(anh, (0, 0), (400, 32), (30, 30, 30), -1)
    cv2.putText(anh, f"#{1000 + i}  {'NG' if ng else 'OK'}  {int(rng.integers(24, 33))} ms",
                (10, 22), cv2.FONT_HERSHEY_SIMPLEX, 0.6, mau, 2)
    khung_hinh.append(Image.fromarray(cv2.cvtColor(anh, cv2.COLOR_BGR2RGB)))

Path("docs").mkdir(exist_ok=True)
khung_hinh[0].save("docs/demo.gif", save_all=True, append_images=khung_hinh[1:],
                   duration=400, loop=0, optimize=True)                     # 400 ms/khung, lặp vô hạn
print(len(khung_hinh), "khung,", Path("docs/demo.gif").stat().st_size // 1024, "KB")

Quang học và camera

Hỏi: Cần phát hiện vết lỗi 0,2 mm trên chi tiết 100 × 75 mm. Chọn camera thế nào?
Trả lời mẫu: Lấy FOV có biên, ví dụ 110 × 82 mm. Muốn vết lỗi phủ ít nhất 3–4 pixel thì kích thước pixel trên vật ≤ 0,2/4 = 0,05 mm, nên cần ≥ 110/0,05 = 2200 pixel theo chiều ngang và ≥ 82/0,05 = 1640 pixel theo chiều dọc: camera 2 MP (1600 × 1200) không đủ, 5 MP (2448 × 2048) cho khoảng 0,045 mm/pixel, đạt. Sau đó chọn ống kính theo khoảng cách làm việc và kích thước cảm biến, kiểm tra độ sâu trường ảnh và độ phân giải quang học của ống kính có tương xứng pixel không.

Hỏi: Khi nào dùng ống kính telecentric?
Trả lời mẫu: Khi đo kích thước mà chi tiết có thể lệch độ cao hoặc có chiều sâu: ống kính thường làm vật gần trông to hơn (sai số phối cảnh), telecentric giữ độ phóng đại gần như không đổi trong dải làm việc. Đánh đổi: đắt, to, FOV bị giới hạn bởi đường kính thấu kính trước.

Chiếu sáng

Hỏi: Vết xước trên bề mặt kim loại bóng khó thấy. Bạn thử đèn gì?
Trả lời mẫu: Đèn góc thấp (dark field): bề mặt phẳng phản xạ ánh sáng đi ra ngoài nên tối, mép xước tán xạ ánh sáng vào camera nên sáng lên, tương phản cao. Nếu bề mặt cong và bóng gây chói, dùng đèn vòm (dome) để chiếu khuếch tán đều. Để đo biên dạng thì dùng đèn nền (backlight). Luôn thêm strobe và kính lọc/bước sóng phù hợp để loại ánh sáng môi trường, và kiểm chứng bằng bộ mẫu có lỗi nhỏ nhất.

Hiệu chuẩn và đo lường

Hỏi: Làm sao biết phép đo của trạm đủ tin cậy?
Trả lời mẫu: Hiệu chuẩn mm/pixel bằng tấm chuẩn (lưới chấm hoặc bàn cờ) có chứng nhận, kiểm tra phần dư; rồi nghiên cứu hệ thống đo: đo lặp lại nhiều chi tiết nhiều lần để tính %GRR so với dung sai (≤ 10% tốt, 10–30% cân nhắc, > 30% không chấp nhận), so với CMM để biết bias, và thử tuyến tính trên dải kích thước. Ở Capstone 1, %GRR tốt nhưng thử tuyến tính lộ ra sai số hệ thống 12 µm, sửa bằng bù biên theo loại kích thước.

Chỉ số OK/NG

Hỏi: Mô hình của bạn accuracy 99%. Như vậy tốt chưa?
Trả lời mẫu: Chưa đủ thông tin. Nếu 1% sản phẩm là NG, mô hình luôn trả OK cũng đạt 99% accuracy mà lọt toàn bộ lỗi. Tôi báo escape (NG bị cho qua) và overkill (OK bị loại) riêng, kèm cỡ mẫu và tập test tách theo lô. Ngưỡng chọn theo chi phí: escape đến tay khách hàng thường đắt hơn overkill nhiều lần, nên chọn ngưỡng sao cho escape = 0 trên tập val, rồi báo overkill phải trả.

Hỏi: Test 300 mẫu NG, không lọt mẫu nào. Có nói tỉ lệ lọt bằng 0 được không?
Trả lời mẫu: Không. 0/300 chỉ cho biết tỉ lệ lọt nhỏ, với độ tin cậy 95% thì cận trên khoảng 3/300 = 1% (quy tắc "rule of three"). Muốn khẳng định tỉ lệ lọt dưới 0,1% cần khoảng 3000 mẫu NG không lọt. (Xem Bài 3.)

Triển khai

Hỏi: Mô hình đúng trong Python nhưng sai trên máy trạm C#. Bạn làm gì?
Trả lời mẫu: 9/10 trường hợp là tiền xử lý khác: thứ tự kênh BGR/RGB, chia 255, mean/std, kiểu nội suy khi resize, layout HWC/NCHW. Tôi xuất một bộ ảnh vàng kèm logit mong đợi và tổng từng kênh tensor; phía C# chạy parity test, so tổng kênh trước để khoanh vùng lỗi tiền xử lý hay lỗi gọi mô hình. Sau đó mới xét sai số số học (FP16/INT8).

Hỏi: Trạm chạy tốt 3 tuần rồi tỉ lệ NG tăng gấp đôi. Bạn điều tra thế nào?
Trả lời mẫu: Xem log có cấu trúc: tỉ lệ NG theo giờ, theo ca, theo lô; phân bố điểm của mô hình và các chỉ số ảnh (độ sáng, độ nét) so với đường cơ sở lúc nghiệm thu. Nếu độ sáng/độ nét trôi thì nghi đèn lão hóa, kính bẩn, camera lệch nét; chạy bộ mẫu chuẩn để xác nhận. Nếu ảnh ổn mà điểm trôi, có thể vật liệu đổi lô: lấy mẫu NG cho QA xác nhận bằng mắt. Không đổi ngưỡng cho "đẹp số" trước khi biết nguyên nhân.

Hỏi: Bắt tay với PLC thế nào để không mất kết quả?
Trả lời mẫu: PLC đặt TRIGGER, trạm chụp và xử lý, ghi kết quả và mã lỗi vào thanh ghi trước, rồi mới bật DONE; PLC đọc kết quả khi thấy DONE và hạ TRIGGER; trạm hạ DONE. Có timeout ở cả hai phía, có giá trị LỖI riêng (không bao giờ mặc định OK khi xử lý thất bại), và bộ đếm chu kỳ để phát hiện mất đồng bộ.

Câu hỏi hành vi

Chuẩn bị 3 câu chuyện theo khung STAR (Situation, Task, Action, Result: bối cảnh, nhiệm vụ, hành động, kết quả), mỗi câu chuyện 2 phút: một lỗi khó bạn tìm ra (ví dụ pixel-locking ở Capstone 1), một lần chọn đánh đổi (escape/overkill ở Capstone 3), một lần làm việc với người khác (kỹ sư PLC, QA, công nhân vận hành). Kết thúc mỗi câu chuyện bằng một con số.

Bài kiểm tra thực hànhNhiều công ty cho bài làm tại chỗ hoặc mang về: đếm vật trên ảnh, đo đường kính lỗ, phát hiện vật thiếu, đọc mã. Họ chấm cách bạn kiểm chứng (ảnh khó, trường hợp không có vật, báo lỗi thay vì báo OK) nhiều hơn chấm thuật toán. Luyện lại các bài của chặng OpenCV và Measurement với yêu cầu: có hàm kiểm thử, có xử lý ảnh xấu.

8. Script kiểm tra README và repo trước khi gửi link

Script sau chấm một repo theo các tiêu chí của bài: dòng mở đầu có con số, demo ở gần đầu, bảng kết quả với chỉ số công nghiệp, mục giới hạn, lệnh chạy, không có đường dẫn cá nhân hay bí mật, không có file nặng hoặc file trọng số lẫn trong repo, có LICENSE và .gitignore:

import re
from pathlib import Path

CHI_SO = r"escape|overkill|p99|cycle time|%GRR|GRR|lọt lỗi|loại nhầm"


def cham_readme(van_ban):
    dong = van_ban.splitlines()
    dau = "\n".join(dong[:15])
    tieu_chi = {
        "Tiêu đề + câu bài toán có con số": bool(re.search(r"^# .+", van_ban, re.M))
                                           and bool(re.search(r"\d", "\n".join(dong[1:6]))),
        "Demo (gif/mp4/ảnh) trong 15 dòng đầu": bool(re.search(r"\.(gif|mp4|png|jpg)\b", dau, re.I)),
        "Bảng kết quả có chỉ số công nghiệp": bool(re.search(r"^\|.*(" + CHI_SO + r")", van_ban, re.M | re.I)),
        "Kết quả có cỡ mẫu (x / N)": bool(re.search(r"\d+\s*/\s*\d+", van_ban)),
        "Có mục quyết định kỹ thuật": bool(re.search(r"^##.*(quyết định|decision|thiết kế)", van_ban, re.M | re.I)),
        "Có mục giới hạn": bool(re.search(r"^##.*(giới hạn|limitation)", van_ban, re.M | re.I)),
        "Có lệnh chạy": bool(re.search(r"`(python|docker|bash|make)[^`]*`", van_ban)),
        "Không có đường dẫn cá nhân": not re.search(r"[A-Z]:\\Users\\|/home/\w+/", van_ban),
        "Không có mật khẩu/khóa": not re.search(r"(password|api[_-]?key|token)\s*[:=]\s*\S+", van_ban, re.I),
    }
    return tieu_chi


def cham_repo(goc, gioi_han_mb=50):
    goc = Path(goc)
    van_de = []
    for f in ("README.md", "LICENSE", ".gitignore", "requirements.txt"):
        if not (goc / f).exists():
            van_de.append(f"thiếu {f}")
    for p in sorted(goc.rglob("*")):
        if not p.is_file() or ".git" in p.parts:
            continue
        mb = p.stat().st_size / 1e6
        if mb > gioi_han_mb:
            van_de.append(f"{p.relative_to(goc)}: {mb:.0f} MB (GitHub chặn file > 100 MB)")
        if p.suffix in (".pt", ".pth", ".ckpt") or p.name == ".env":
            van_de.append(f"{p.relative_to(goc)}: không nên đưa lên repo")
    return van_de


def bao_cao(goc):
    tc = cham_readme((Path(goc) / "README.md").read_text(encoding="utf-8"))
    print(f"== {goc}: README {sum(tc.values())}/{len(tc)}")
    for ten, dat in tc.items():
        if not dat:
            print("   [ ]", ten)
    for v in cham_repo(goc):
        print("   [!]", v)

Xem đáp án

Trình tự cho mỗi capstone:

  1. Chạy lại toàn bộ dự án từ đầu bằng một lệnh trên máy sạch (môi trường ảo mới); sửa đến khi chạy được. Lệnh đó ghi vào mục "Chạy lại toàn bộ".

Bài 3. Câu hỏi phỏng vấn: "Trạm của bạn không lọt mẫu nào trong n mẫu NG. Với độ tin cậy 95%, tỉ lệ lọt lỗi thật có thể cao tới bao nhiêu?" Tính chính xác cận trên với n = 30, 300, 3000 và so với quy tắc 3/n. Cần bao nhiêu mẫu NG để khẳng định tỉ lệ lọt dưới 0,1%?

Xem đáp án

Nếu tỉ lệ lọt thật là p, xác suất không lọt mẫu nào trong n mẫu là (1 − p)n. Cận trên 95% là giá trị p mà xác suất đó bằng 5%: p = 1 − 0,051/n ≈ 3/n (vì ln 0,05 ≈ −3).

import math

for n in (30, 300, 3000):
    p = 1 - 0.05 ** (1 / n)
    print(f"0 lọt / {n:4d} mẫu NG: cận trên 95% = {p * 100:.3f} %  (quy tắc 3/n: {300 / n:.3f} %)")
n_can = math.ceil(math.log(0.05) / math.log(1 - 0.001))
print("Để khẳng định tỉ lệ lọt < 0,1 % cần", n_can, "mẫu NG không lọt mẫu nào")

0 lọt /  300 mẫu NG: cận trên 95% = 0.994 %  (quy tắc 3/n: 1.000 %)
0 lọt / 3000 mẫu NG: cận trên 95% = 0.100 %  (quy tắc 3/n: 0.100 %)
Để khẳng định tỉ lệ lọt < 0,1 % cần 2995 mẫu NG không lọt mẫu nào

Đây cũng là lý do giám sát sau triển khai (kiểm tra mẫu chuẩn mỗi ca, theo dõi drift) quan trọng: tập thử không bao giờ đủ lớn để chứng minh mọi thứ.
