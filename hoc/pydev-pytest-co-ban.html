pytest cơ bản: viết test, fixture, parametrize, đo coverage

Kiểm thử tự động với pytest: assert, cấu trúc thư mục tests, fixture, parametrize, pytest.raises, tmp_path, monkeypatch và coverage.

  • Viết test bằng assert và chạy pytest
  • Dùng fixture, parametrize, tmp_path, kiểm tra ngoại lệ
  • Đo độ phủ test bằng pytest-cov

Bạn sửa một dòng trong hàm tính tiền điện để thêm bậc mới. Làm sao chắc rằng các mức cũ vẫn tính đúng? Chạy tay thử vài số mỗi lần sửa thì chậm và dễ sót. Test tự động là những đoạn code kiểm tra code của bạn, chạy hàng trăm phép thử trong một giây mỗi khi có thay đổi. pytest là công cụ kiểm thử phổ biến nhất của Python, và viết test là kỹ năng phân biệt rõ nhất giữa người viết script và Python Developer.

1. Test đầu tiên

Cấu trúc dự án (theo kiểu uv init ở bài trước):

tien-dien/
├── pyproject.toml
├── src/
│   └── tien_dien/
│       └── __init__.py      ← hàm tinh_tien_dien (bài thực hành chặng 1, thêm kiểm tra số âm)
└── tests/
    └── test_tien_dien.py

File src/tien_dien/__init__.py:

"""Tính tiền điện sinh hoạt theo bậc thang."""

BAC_GIA = [(50, 1984), (100, 2050), (200, 2380), (300, 2998), (400, 3350), (None, 3460)]


def tinh_tien_dien(so_kwh: int) -> int:
    """Tiền điện (đồng, chưa thuế) cho so_kwh kWh."""
    if so_kwh < 0:
        raise ValueError("Số kWh không được âm")
    con_lai, muc_duoi, tong = so_kwh, 0, 0
    for muc_tran, gia in BAC_GIA:
        if con_lai <= 0:
            break
        do_rong = con_lai if muc_tran is None else muc_tran - muc_duoi
        kwh = min(con_lai, do_rong)
        tong += kwh * gia
        con_lai -= kwh
        muc_duoi = muc_tran or muc_duoi
    return tong

File tests/test_tien_dien.py:

# (minh họa) cần package tien_dien ở trên
from tien_dien import tinh_tien_dien


def test_khong_dung_dien():
    assert tinh_tien_dien(0) == 0


def test_tron_bac_1():
    assert tinh_tien_dien(50) == 50 * 1984

Thêm pytest và cấu hình vào pyproject.toml, rồi chạy:

[tool.pytest.ini_options]
pythonpath = ["src"]       # chỉ cần nếu dự án chưa được cài vào môi trường (uv đã tự cài)
testpaths = ["tests"]

$ uv add --dev pytest
$ uv run pytest
============================= test session starts =============================
collected 2 items

tests\test_tien_dien.py ..                                               [100%]

============================== 2 passed in 0.02s ==============================

Quy ước của pytest: file tên test_*.py, hàm tên test_*, kiểm tra bằng lệnh assert thông thường của Python. Mỗi dấu chấm là một test đạt. Tùy chọn hay dùng: -v (in tên từng test), -q (gọn), -x (dừng ở lỗi đầu tiên), -k tron (chỉ chạy test có chữ "tron" trong tên).

2. Khi test thất bại

Giả sử bạn vô tình xóa dòng muc_duoi = muc_tran or muc_duoi. pytest chỉ ra chính xác chỗ sai:

.....FF.                                                                 [100%]
================================== FAILURES ===================================
__________________________ test_cac_moc[150-320700] ___________________________

so_kwh = 150, mong_doi = 320700

    def test_cac_moc(so_kwh, mong_doi):
>       assert tinh_tien_dien(so_kwh) == mong_doi
E       assert 304200 == 320700
E        +  where 304200 = tinh_tien_dien(150)

tests\test_tien_dien.py:25: AssertionError

pytest phân tích biểu thức assert và in cả giá trị thực tế (304200) lẫn giá trị mong đợi (320700), không cần bạn tự viết thông báo lỗi. Để ý: với lỗi này, các mức 51 và 100 kWh vẫn đúng, chỉ từ bậc 3 trở đi mới sai. Nếu chỉ thử tay vài số nhỏ, bạn sẽ không phát hiện ra. Đó là lý do cần test cho mọi mốc quan trọng.

3. parametrize: một test, nhiều bộ dữ liệu

# (minh họa) thêm vào tests/test_tien_dien.py
import pytest

from tien_dien import tinh_tien_dien


@pytest.mark.parametrize(
    ("so_kwh", "mong_doi"),
    [
        (1, 1984),
        (51, 99_200 + 2050),
        (100, 99_200 + 102_500),
        (150, 320_700),
        (420, 1_143_700),
    ],
)
def test_cac_moc(so_kwh, mong_doi):
    assert tinh_tien_dien(so_kwh) == mong_doi


def test_so_am_bao_loi():
    with pytest.raises(ValueError, match="không được âm"):
        tinh_tien_dien(-1)

  • @pytest.mark.parametrize chạy cùng một hàm test với từng bộ tham số; mỗi bộ là một test riêng có tên riêng.
  • pytest.raises(LoaiLoi, match="...") là context manager kiểm tra khối lệnh phải ném đúng loại ngoại lệ với thông điệp khớp mẫu. Test hành vi lỗi quan trọng không kém test kết quả đúng.

Chọn dữ liệu test thế nào? Giá trị biên (0, 50, 51, 100, 101), một giá trị điển hình mỗi vùng, giá trị cực lớn và dữ liệu không hợp lệ.

4. Fixture: chuẩn bị dữ liệu dùng chung

# (minh họa) tests/test_thu_vien.py, dùng lõi thư viện ở dự án chặng 4
from datetime import date

import pytest

from thu_vien import Sach, SachDangDuocMuon, ThanhVien, ThuVien


@pytest.fixture
def tv() -> ThuVien:
    """Một thư viện có 2 sách, 1 thành viên; tạo mới cho MỖI test."""
    t = ThuVien()
    t.them_sach(Sach("S01", "Số đỏ", "Vũ Trọng Phụng"))
    t.them_sach(Sach("S02", "Clean Code", "Robert C. Martin"))
    t.them_thanh_vien(ThanhVien("TV1", "An"))
    return t


def test_muon_roi_khong_muon_lai_duoc(tv):
    tv.muon("S01", "TV1", date(2026, 10, 1))
    with pytest.raises(SachDangDuocMuon):
        tv.muon("S01", "TV1", date(2026, 10, 2))


def test_luu_va_nap_giu_nguyen_du_lieu(tv, tmp_path):
    tv.muon("S02", "TV1", date(2026, 10, 1))
    p = tmp_path / "tv.json"
    tv.luu(p)
    tv2 = ThuVien.nap(p)
    assert set(tv2.sach) == {"S01", "S02"}
    assert tv2.dang_muon["S02"].han_tra == date(2026, 10, 15)
  • Hàm có @pytest.fixture chuẩn bị dữ liệu; test nào cần thì khai báo tham số trùng tên, pytest tự gọi fixture và truyền vào.
  • Mỗi test nhận một bản mới, nên test này mượn sách không ảnh hưởng test khác. Các test phải độc lập, chạy theo thứ tự nào cũng đúng.
  • tmp_path là fixture có sẵn: một thư mục tạm riêng cho mỗi test, tự dọn sau đó. Không bao giờ để test ghi vào file thật của dự án.
  • Fixture dùng chung cho nhiều file test đặt trong tests/conftest.py, pytest tự tìm thấy mà không cần import.

5. monkeypatch: thay thế thứ khó kiểm soát

# (minh họa) code dùng biến môi trường và thời gian thực
import os


def che_do() -> str:
    return os.environ.get("CHE_DO", "phat_trien")


def test_che_do_san_xuat(monkeypatch):
    monkeypatch.setenv("CHE_DO", "san_xuat")     # chỉ có hiệu lực trong test này
    assert che_do() == "san_xuat"


def test_che_do_mac_dinh(monkeypatch):
    monkeypatch.delenv("CHE_DO", raising=False)
    assert che_do() == "phat_trien"

monkeypatch tạm thay biến môi trường, thuộc tính, hàm (ví dụ thay hàm gọi mạng bằng hàm trả dữ liệu giả) và tự khôi phục sau test. Tuy vậy, cách tốt nhất vẫn là thiết kế để không cần nó: truyền hom_nay, truyền kênh gửi vào như các dự án trước. Code dễ test thường cũng là code thiết kế tốt.

6. Đo độ phủ (coverage)

$ uv add --dev pytest-cov
$ uv run pytest --cov=tien_dien --cov-report=term-missing
Name                        Stmts   Miss  Cover   Missing
---------------------------------------------------------
src\tien_dien\__init__.py      14      0   100%
---------------------------------------------------------
TOTAL                          14      0   100%

Coverage cho biết dòng nào chưa có test nào chạy qua (cột Missing). Hữu ích để tìm nhánh bị bỏ quên, nhưng 100% không có nghĩa là không có lỗi: nó chỉ nói dòng đã được chạy, không nói kết quả đã được kiểm tra đủ.

Tóm tắt

  • File tests/test_*.py, hàm test_*, kiểm tra bằng assert; chạy uv run pytest.
  • @pytest.mark.parametrize cho nhiều bộ dữ liệu; pytest.raises cho ngoại lệ.
  • Fixture chuẩn bị dữ liệu, mỗi test một bản mới; tmp_path, monkeypatch có sẵn; dùng chung đặt ở conftest.py.
  • Test giá trị biên; dùng coverage để tìm chỗ chưa test.

Bài tập

Bài 1. Test tiền điện

Dựng dự án tien-dien như mục 1, viết đủ test ở mục 1 và 3 (gồm các mốc ranh giới) và chạy đạt 8/8. Sau đó cố tình làm sai hàm theo hai cách khác nhau, xác nhận test bắt được cả hai.

Xem gợi ý

Hai lỗi nên thử: đổi giá bậc 2 thành 2.500 (test 51 và 100 kWh phải đỏ), và đổi if con_lai <= 0 thành if con_lai < 0 (test có đỏ không? Nếu không, hãy giải thích vì sao lỗi này vô hại). Viết test để kiểm tra rằng test bắt được lỗi là cách nghĩ của "mutation testing".

Bài 2. Test lõi thư viện

Viết file test cho lõi thư viện chặng 4 dùng fixture tv và tmp_path: mượn, trả đúng hạn (trả 0), trả muộn (trả số ngày quá hạn), sách không tồn tại, lưu và nạp.

Xem đáp án

Ngoài hai test ở mục 4, thêm:

# (minh họa) nối vào tests/test_thu_vien.py
from thu_vien import KhongTimThay


@pytest.mark.parametrize(("ngay_tra", "qua_han"), [(date(2026, 10, 15), 0), (date(2026, 10, 18), 3)])
def test_tra_sach(tv, ngay_tra, qua_han):
    tv.muon("S01", "TV1", date(2026, 10, 1))      # hạn trả 15/10
    assert tv.tra("S01", ngay_tra) == qua_han
    assert "S01" not in tv.dang_muon


def test_muon_sach_khong_ton_tai(tv):
    with pytest.raises(KhongTimThay, match="S99"):
        tv.muon("S99", "TV1", date(2026, 10, 1))
$ uv run pytest -q
.....                                                                    [100%]
5 passed in 0.03s

Ngày trả đúng hạn chót (15/10) phải trả về 0: đây chính là giá trị biên dễ sai nhất nếu viết >= thay vì >.

Nguồn tham khảo: pytest: Get Started; How to use fixtures; How to parametrize; pytest-cov.

Bài tập thực hành

  1. Viết 6 test cho hàm tinh_tien_dien ở chặng 1, gồm các mốc ranh giới bậc thang, dùng parametrize.
  2. Viết test cho lớp ThuVien dùng fixture và tmp_path để kiểm tra lưu, nạp JSON.

Làm xong bài tập mới chuyển sang bài tiếp theo: tự viết code là cách duy nhất để nhớ lâu.
